## Контекст

Сертификат или паспорт подтверждает качество **сразу нескольких типоразмеров**:
один протокол испытаний охватывает партию труб разных диаметров, один сертификат
соответствия распространяется на весь типоразмерный ряд изделия. Обратная
ситуация столь же штатна: у одного типоразмера есть паспорт, сертификат
соответствия, протокол испытаний и декларация, выданные разными организациями с
разными номерами и сроками.

Значит, отношение «документ ↔ типоразмер» — **многие ко многим**. Таблица
`document_variants` и обе симметричные ORM-связи (`Document.variants`,
`ProductVariant.documents`) существуют с миграции `056121f44e99`, но до
TASK-DOC-007B–007D были доступны **только из Python**: ни маршрутов привязки, ни
поиска по материалу не было.

Пользовательский сценарий, ради которого принято решение:

> Создать материал и три типоразмера → создать сертификат → загрузить PDF →
> привязать сертификат к трём размерам → найти сертификат по `Ø63` → открыть
> карточку → скачать PDF.

Этот ADR фиксирует утверждённые правила и подтверждённую реализацию; новые
бизнес-функции он не вводит.

## Принятое решение

### Базовая привязка MVP: `Document ↔ ProductVariant`

**Привязка документа выполняется к типоразмеру, а не к изделию или партии.**
Именно `ProductVariant` — то звено, через которое достигаются и `Product`
(материал), и `Manufacturer` (производитель): `ProductVariant.product_id →
Product.id`, `Product.manufacturer_id → Manufacturer.id`.

Связь — **many-to-many** через существующую таблицу `document_variants`
(составной первичный ключ `(document_id, variant_id)`, `ON DELETE CASCADE` на
обоих внешних ключах, индекс `ix_document_variants_variant_id`). Новых таблиц и
миграций не потребовалось.

Следствия:

- **Один документ охватывает несколько типоразмеров** — набор привязок свободно
  состоит из любого числа вариантов.
- **Один типоразмер охватывается несколькими документами** — ограничений в
  обратную сторону нет.

### HTTP-контракт привязок

Привязки живут в собственном модуле `app/api/document_variants/` и свисают с
того же сегмента `/documents/{document_id}`, что и вложения:

| Метод и путь | Семантика |
| --- | --- |
| `GET /documents/{document_id}/variants` | **Чтение** текущего набора привязок. Голый массив `ProductVariantRead`, порядок `ProductVariant.id ASC`. Документа нет → `404`; привязок нет → `200 []` |
| `PUT /documents/{document_id}/variants` | **Атомарная полная замена** набора. Тело — `{"variant_ids": [...]}`; ответ — новый набор тем же массивом `ProductVariantRead` |

Правила `PUT`:

1. **Полная замена, а не добавление.** Присланный список становится набором
   целиком: то, чего в нём нет, отвязывается.
2. **`variant_ids` — первичные ключи `ProductVariant`**, не диаметры и не
   `size_text`. Идентификатор выбирает клиент, потому что только клиент знает
   точный вариант материала.
3. **Пустой список очищает привязки** — `{"variant_ids": []}` снимает все связи и
   возвращает `200 []`.
4. **Повторный `PUT` идемпотентен.** Тот же набор, поданный снова, даёт тот же
   ответ `200` и не меняет ни состояние базы, ни историю.
5. **Привязка не изменяет `verification_status` и не создаёт `reopened`.**
   Состав привязок не входит в значимые реквизиты документа: замена набора у
   `verified` оставляет его `verified` и **не пишет** событие
   `significant_fields_changed`. Это отличие от состава вложений
   ([ADR-009](ADR-009-document-attachments.md), правило 4) — сознательное.
6. **Отсутствующий вариант — ошибка `422`, а не частичная запись.** Если хотя бы
   один `variant_id` не существует, операция отклоняется целиком, и прежний
   набор остаётся нетронутым: либо меняются все привязки, либо ни одна.

Маршруты **тонкие**: роутер не выполняет SQL, не коммитит, не откатывает и не
берёт `FOR UPDATE`. Всё это — в сервисе.

### `DocumentVariantService`

Две операции, обе — `@staticmethod` над сессией вызывающего:

| Метод | Поведение |
| --- | --- |
| `list_variants(db, document_id)` | Чтение. Документа нет → `DocumentNotFoundError`; привязок нет → `[]`; порядок `id ASC` |
| `set_variants(db, document_id, variant_ids)` | Полная замена. Возвращает прочитанный набор — **отсоединённые** объекты с закрытой читающей транзакцией |

Транзакционная модель повторяет `FileService` ([ADR-009](ADR-009-document-attachments.md)):
одна транзакция на операцию, **один `commit`**, первая блокировка документа через
общий `transaction.locked_document`, без промежуточных коммитов. Чужую
транзакцию на входе сервис **отвергает** (`TransactionAlreadyOpenError`).
Незавершённые изменения вызывающего переводятся в
`UncommittedDocumentChangesError`. Порядок проверок: дубли → владение
транзакцией → блокировка → существование ссылок.

Дубли `variant_id` в теле запроса отклоняются **дважды**: схемой
(`DocumentVariantLinkRequest`), и, как запасной рубеж, сервисом
(`DuplicateVariantIdsError`). Все отсутствующие идентификаторы собираются в одну
ошибку `ProductVariantsNotFoundError`, а не сообщается по одному.

### Поиск: материальные фильтры через `document_variants`

`GET /documents` расширен **необязательными** query-параметрами; отдельного
маршрута `/documents/search` нет:

| Параметр | Семантика |
| --- | --- |
| `material` | подстрока в `Product.name`, регистронезависимо |
| `standard` | подстрока в `Product.standard`, регистронезависимо |
| `size_text` | **точное** `ProductVariant.size_text` |
| `variant_id` | точный `ProductVariant.id` |
| `manufacturer_id` | точный `products.manufacturer_id` |
| `number` | подстрока в `Document.number`, регистронезависимо |
| `status` | одно из `pending` / `verified` / `rejected` |
| `limit`, `offset` | прежняя пагинация (1–100, ≥ 0) |

Правила поиска:

1. **Все заданные фильтры соединяются логическим И.** Без параметров сохраняется
   прежнее поведение коллекции. Ответ — прежний голый массив `DocumentOut`,
   сортировка `Document.id ASC`, пагинация применяется после фильтрации.
2. **Материальные фильтры сопоставляются одному `ProductVariant`.** `material`,
   `standard`, `size_text`, `variant_id` и `manufacturer_id` описывают один и тот
   же вариант, поэтому применяются внутри **одного коррелированного `EXISTS`** по
   цепочке `document_variants → product_variants → products`. Документ
   возвращается, только если **один** его вариант удовлетворяет всем условиям
   сразу. Два фильтра не могут быть удовлетворены двумя разными вариантами:
   сертификат на `SDR11 Ø32` + `SDR17 Ø63` **не** находится по
   `material=SDR11&size_text=Ø63`.
3. **Документ не дублируется.** `EXISTS` — полу-соединение: сколько бы вариантов
   ни совпало, документ возвращается один раз; `DISTINCT` не нужен, а `LIMIT` /
   `OFFSET` считают документы, а не строки соединения.
4. **`size_text` — точное сопоставление, без нормализации.** `Ø63` не равно
   `Ø 63` и не равно `ø63`. Приведение размеров к канонической форме не вводится:
   это отдельное решение, связанное с [ADR-006](ADR-006-unique-size-within-product.md).
5. **`products.standard` — источник поля ГОСТ/ТУ.** Отдельной сущности
   «стандарт» нет: строка хранится у `Product` вместе с наименованием.
6. **Поиск по `number` и `status` относится непосредственно к `Document`.**
   Это реквизиты самого документа, а не его материала.
7. **Регистронезависимость — через `lower(...)`, без `ILIKE`.** `%`, `_` и
   разделитель шаблона в пользовательском вводе экранируются: `material=100%`
   ищет литерал, а не «начинается с 100».
8. **Несуществующий `variant_id` или `manufacturer_id` — не `404`, а `200 []`.**
   «Такого типоразмера нет» и «ни один документ его не покрывает» для поиска —
   один и тот же ответ.
9. **Пустой или пробельный текстовый фильтр — `422`,** а не молчаливое «без
   фильтра».

### Что в MVP не участвует

- **`document_products` и `document_batches` сохраняются**, но в привязке и
  материальном поиске MVP **не участвуют**. Семантика связи документа с
  изделием и партией не утверждена; материальный поиск опирается **только** на
  `document_variants`. Документ, связанный лишь через `document_products`, по
  материальному фильтру не находится.
- **`diameter` не фильтруется.** Числовой `product_variants.diameter` необязателен
  и может быть `NULL`; надёжный признак размера — `size_text`, по нему и идёт
  поиск. Вариант с `diameter = NULL` находится по `size_text`.
- **Автоматической нормализации размеров, полнотекстового поиска, новых
  индексов, отдельного `DELETE` привязки и новых миграций нет.** Снятие одной
  связи выполняется `PUT` с укороченным набором, а очистка — `PUT` с пустым.

## Контракт ошибок

| Ситуация | Ответ |
| --- | --- |
| Документ не найден (`GET` / `PUT` привязок) | `404` |
| `variant_ids` ссылается на несуществующий вариант | `422` |
| Дубли `variant_id` в теле | `422` (схема; сервис — запасной рубеж) |
| Некорректное тело запроса | `422` |
| Транзакция открыта на входе | `409` |
| Незавершённые изменения в сессии | `409` |
| Любая иная ошибка | `500`, без SQL, путей и трассировки |

## Последствия

**Положительные**

- Сертификат на несколько типоразмеров привязывается и находится **через HTTP**,
  без прямых SQL-запросов; сквозной сценарий «труба → Ø63 → PDF» проверен
  интеграционным набором.
- Ложные совпадения исключены конструкцией запроса, а не дисциплиной вызывающего:
  один `EXISTS` не допускает «склейку» фильтров из разных вариантов.
- Регистронезависимость и защита шаблона собраны в одном месте —
  `DocumentService._contains_ci`.
- Нулевая стоимость схемы: новая функциональность построена на существующих
  таблицах, миграция не понадобилась.

**Отрицательные**

- **Изменение набора привязок пока не журналируется отдельно.** В отличие от
  вложений (`reopened` с причиной `file_added` / `file_deleted`), история
  проверок не фиксирует, когда сертификат «пристегнули» к новому размеру.
- Поиск с ведущим `%` не использует btree; при росте объёма потребуется индекс
  `pg_trgm`/GIN — это отдельное задание.
- Регистронезависимость опирается на `lower()` и collation базы; смена collation
  может изменить поведение для не-ASCII.

## Ограничения

- **Изменения набора привязок не журналируются.** Отдельное событие истории для
  «привязали / отвязали типоразмер» в MVP не вводится; если понадобится —
  это новый вид записи и новое решение.
- **Каскадное удаление связано с открытым вопросом.** В базе у обоих внешних
  ключей `document_variants` объявлен `ON DELETE CASCADE`, поэтому физическое
  удаление `ProductVariant` унесёт и привязки. Но удаление самих материалов и
  типоразмеров ещё не реализовано и семантика такого каскада **не утверждена**;
  она потребует отдельного решения.
- **Семантика одновременной привязки к `Product` и `ProductVariant` не
  определена.** Технически `document_products` и `document_variants` могут
  указывать на один материал одновременно; поисковая семантика такого
  дублирования не установлена, и в MVP `document_products` не участвует.
- **Поиск по диаметру не реализован** — `diameter` может быть `NULL`; источник
  размера — `size_text`.
- **Анонимность.** Привязка и поиск доступны без аутентификации. **Публичное
  развёртывание анонимных маршрутов запрещено** до реализации аутентификации и
  авторизации: поиск раскрывает состав документации, а `PUT` меняет связи без
  проверки прав. До этого маршруты доступны только в локальной среде разработки.

## Связь с текущей реализацией

- **[ADR-005](ADR-005-one-sdr-one-product.md)** — разные SDR — это разные
  `Product`, поэтому привязка строится через `ProductVariant`, а не через
  `Product`: типоразмерный ряд одного изделия не смешивается с другим.
- **[ADR-006](ADR-006-unique-size-within-product.md)** — уникальность
  `(product_id, size_text)` делает размер однозначным, поэтому точное
  сопоставление `size_text` в поиске не порождает неоднозначности.
- **[ADR-008](ADR-008-document-verification-lifecycle.md)** — состав привязок не
  входит в значимые реквизиты, поэтому он не запускает возврат в `pending` и не
  пишет `reopened`.
- **[ADR-009](ADR-009-document-attachments.md)** — общий механизм транзакции и
  блокировки (`app/services/transaction.py`) переиспользован; `set_variants`
  владеет одной транзакцией и коммитит ровно один раз, как `attach` / `detach`.
  В отличие от вложений, изменение привязок вердикт документа не сбрасывает.
- **[DOCUMENT-VARIANT-RELATIONSHIP.md](DOCUMENT-VARIANT-RELATIONSHIP.md)** —
  черновик, впервые подтвердивший требование и структуру данных; номер ADR
  присвоен здесь. Документ сохранён как историческая справка.

## Нерешённые вопросы

1. **Привязка на уровне `Product` и `Batch`** — когда и зачем, если типоразмер
   уже выбран; семантика одновременной привязки к `Product` и `ProductVariant`.
2. **Действие при каскадном удалении `ProductVariant`**, к которому привязаны
   документы: оставлять привязку, запрещать удаление или требовать отвязки.
3. **Поиск по диаметру** — по числовому `diameter` (`NULL`-able) или только по
   `size_text`.
4. **Журналирование изменений привязок** — нужен ли отдельный вид события.
5. **Индексы под `LIKE '%…%'`** — `pg_trgm`/GIN, когда объём данных оправдает
   миграцию.
