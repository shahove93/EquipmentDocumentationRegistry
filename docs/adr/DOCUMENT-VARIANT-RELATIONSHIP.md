## Контекст

Сертификат или паспорт может подтверждать качество **сразу нескольких
типоразмеров**: один протокол испытаний охватывает партию труб разных диаметров,
один сертификат соответствия распространяется на весь типоразмерный ряд изделия.

Обратная ситуация столь же штатна: один типоразмер входит в несколько документов —
паспорт, сертификат соответствия, протокол испытаний, декларация. При этом они
выданы разными организациями и имеют разные номера и сроки действия.

Значит, отношение между документами и типоразмерами — **многие ко многим**, а не
владение «один документ — один вариант».

## Подтверждённое требование

1. **Один сертификат может распространяться на несколько диаметров.**
2. **Один типоразмер может иметь несколько документов.**
3. **Используется связь many-to-many через таблицу `document_variants`.**
4. **Повтор одинаковой пары запрещён составным первичным ключом**
   `(document_id, variant_id)`.

## Реализация

### Таблица связи

```python
class DocumentVariant(Base):
    __tablename__ = "document_variants"
    document_id: Mapped[int] = mapped_column(
        ForeignKey("documents.id", ondelete="CASCADE"), primary_key=True
    )
    variant_id: Mapped[int] = mapped_column(
        ForeignKey("product_variants.id", ondelete="CASCADE"),
        primary_key=True,
        index=True,
    )
```

| Свойство | Значение |
| --- | --- |
| Составной первичный ключ | `(document_id, variant_id)` |
| Индекс | `ix_document_variants_variant_id` на `variant_id` — для выборки «все документы типоразмера» |
| Удаление документа | `ON DELETE CASCADE` — связи удаляются автоматически |
| Удаление типоразмера | `ON DELETE CASCADE` — связи удаляются автоматически |

Индекс на `variant_id` не является частью первичного ключа, поскольку `(id,
variant_id)` уже покрывает направление «документ → варианты». Обратное направление
требует отдельного индекса, и он присутствует.

### Связи в ORM

| Сторона | Объявление |
| --- | --- |
| `Document.variants` | `relationship(secondary="document_variants", back_populates="documents")` |
| `ProductVariant.documents` | `relationship(secondary="document_variants", back_populates="variants")` |

Объявления симметричны, поэтому обе стороны навигируются без дополнительных
запросов к коду документа.

### Миграция

| | |
| --- | --- |
| **Ревизия** | `056121f44e99` |
| **Имя файла** | `alembic/versions/056121f44e99_create_document_link_tables.py` |

Три таблицы связи созданы одной миграцией и построены по одной схеме: составной
первичный ключ, индекс на второй колонке, `ON DELETE CASCADE` на обоих внешних
ключах.

## Связь с другими решениями

- **[ADR-006](ADR-006-unique-size-within-product.md)** — обоснование вводит
  ограничение `UNIQUE(product_id, size_text)` именно тем, что оно обеспечивает
  *однозначность* привязки документа к набору типоразмеров: если бы один и тот же
  размер можно было завести дважды внутри изделия, ссылка на документ стала бы
  неоднозначной.
- **[ADR-005](ADR-005-one-sdr-one-product.md)** — разные SDR — это разные
  `Product`, поэтому один типоразмерный ряд может встречаться в нескольких
  изделиях, и связь строится именно через `ProductVariant`, а не через `Product`.

## Текущее ограничение

**Связь реализована на уровне модели и схемы данных, но недоступна через API.**
В `document_variants` нет ни одного маршрута: создание документа не реализовано,
операций привязки документов к типоразмерам нет. Работа со связями возможна
пока только на уровне ORM и прямых SQL-запросов.

Проверить корректность структуры можно существующими тестами модели:
`tests/test_document_links.py`.

## Что потребуется для API

При проектировании операций привязки следует учитывать:

- порядок валидации: существование `document_id` и каждого `variant_id`;
- атомарность: связь должна сохраняться целиком, частичная запись недопустима;
- идемпотентность: повтор той же пары должен быть безопасен (составной
  первичный ключ это обеспечивает на уровне БД, но поведение API требует
  определения — конфликт 409 или успех без изменений);
- замена набора связей целиком против добавления отдельных пар.
