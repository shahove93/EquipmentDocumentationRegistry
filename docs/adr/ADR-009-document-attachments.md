## Контекст

`FileService` и `LocalStorageBackend` написаны и покрыты 152 тестами, но
**не подключены ни к одному маршруту**: поиск по `app/` вне собственных модулей
не находит ни одной ссылки. Последствие не косметическое — `DocumentService.verify`
требует хотя бы одного прикреплённого файла, поэтому **подтвердить документ
через приложение невозможно**. Подтверждённый жизненный цикл из
[ADR-008](ADR-008-document-verification-lifecycle.md) существует только
программно.

Вторая проблема обнаружилась при проектировании HTTP-слоя. `FileService`
вызывает `self._db.commit()` внутри `_register`, а `DocumentService` коммитит
через собственный `_commit`. Два независимых владельца транзакции означают, что
изменение статуса документа и событие истории не могут попасть в одну
транзакцию с метаданными файла. Правило «изменение статуса и событие истории
сохраняются атомарно» из ADR-008 распространяется и на файловые операции —
а значит, нужен один владелец.

Третья проблема — семантическая. ADR-008 отвечает на вопрос «что происходит при
изменении реквизитов», но не отвечает на вопрос «что происходит при изменении
**вложений**». Вердикт выносится по конкретному скану; если скан заменили или
удалили, прежний вердикт по смыслу устарел, но ни одно правило этого не
описывало.

## Принятое решение

### Правила жизненного цикла вложений

1. **Один документ допускает несколько файлов.** Ограничения на количество нет;
   одинаковое содержимое, загруженное дважды, даёт две независимые строки.
2. **Форматы MVP — PDF, JPEG, PNG.** Тип определяется по сигнатуре содержимого,
   расширение игнорируется.
3. **Максимальный размер одного файла берётся из `MAX_UPLOAD_SIZE_BYTES`**,
   по умолчанию **100 МиБ**. Проверка выполняется на лету, поток прерывается
   при превышении; файл целиком в память не читается.
4. **Успешное добавление или удаление файла у `verified` или `rejected`
   переводит документ в `pending`.** Вердикт относился к прежнему набору
   вложений.
5. **На соответствующий переход создаётся ровно одно событие `reopened`.**
   `from_status` равен прежнему вердикту, `to_status` — `pending`.
6. **Изменение файлов у `pending` не создаёт событие `reopened`.** Возвращать
   нечего, и история не засорялась бы бездействующими строками.
7. **Замена скана в MVP — последовательные операции загрузки и удаления.**
   Отдельной операции замены нет.
8. **Удаление последнего файла разрешено**, но `verified` **предварительно**
   переводится в `pending` **в той же транзакции**. Запрета на удаление
   последнего файла нет: инвариант «подтверждение требует файла» из ADR-008
   сохраняется сам собой, потому что после удаления документ уже не `verified`
   и для повторного подтверждения требует нового вложения.
9. **Повторное удаление отсутствующего файла возвращает `404`** — файл не
   найден, операция не выполняется повторно и второй раз.

### Механизм `record_reopened()`

Создание события `reopened` сосредоточено **в одной функции** без состояния,
используемой и `DocumentService`, и `FileService`:

```
record_reopened(db, document, reason) -> bool
```

- возвращает `True`, если событие создано, и `False`, если документ уже
  `pending` — то есть когда перехода не было;
- читает прежний статус, присваивает `pending`, добавляет
  `DocumentVerificationEvent` в сессию вызывающего и **не коммитит**;
- вызывается под блокировкой документа (§ «Транзакции»).

`DocumentService._apply_status_transition` сводится к вызову этой функции.
**Дублирования бизнес-логики нет**, и будущий переход — третий источник — не
потребует второго места, где пишется `reopened`.

#### Контракт функции

Функция реализована в `app/services/verification_history.py` и принимает ровно
те обязательства, которые перечислены ниже. Всё, чего здесь нет, она не делает.

| Обязательство | Поведение |
| --- | --- |
| Проверка причины | Выполняется **самостоятельно**. Причина вне закрытого множества → `InvalidReopenReasonError` |
| Проверка статуса | Статус вне множества `documents.verification_status` → `UnknownVerificationStatusError` |
| Порядок отказов | Обе проверки выполняются **до изменения ORM-объекта** и до обращения к сессии |
| Документ `pending` | Возвращает `False`; объект и сессия не затрагиваются, событие не создаётся |
| Переход из `verified` / `rejected` | Присваивает `pending` и добавляет ровно одно событие |
| Транзакция | Не вызывает `commit`, `rollback` или `flush`. Единственный `commit` остаётся у вызывающего сервиса |
| Блокировка | **Не выполняет** `SELECT ... FOR UPDATE`. Блокировкой и транзакцией управляет вызывающий сервис |
| Загрузка документа | Не загружает объект самостоятельно — получает ORM-объект сессии вызывающего |

Обе ошибки наследуют `VerificationHistoryError` и несут ошибочное значение на
экземпляре, чтобы вызывающий мог его прочитать без разбора текста сообщения.
Обе — ошибки вызывающего кода, а не условие, порождаемое пользователем: причина
перехода и состояние документа задаются константами внутри программы.

### Поле `reason` в событии истории

`reason` несёт **разные по природе значения в зависимости от `event_type`**, и
это различие обязательно:

| `event_type` | `reason` | Происхождение |
| --- | --- | --- |
| `rejected` | текст, введённый человеком | объяснение отклонения |
| `verified` | необязательный текст или `NULL` | комментарий к решению |
| `reopened` | **машинный код источника перехода** | закрытое множество |

**Закрытое множество `reason` для `reopened`:**

| Значение | Источник перехода |
| --- | --- |
| `significant_fields_changed` | изменён значимый реквизит — `DocumentService.update` |
| `file_added` | добавлено вложение — `FileService` |
| `file_deleted` | удалено вложение — `FileService` |

Значение выбирает вызывающий код, но **проверяет его сама функция**: причина вне
множества приводит к `InvalidReopenReasonError`, и это происходит **до изменения
ORM-объекта** — неверная причина не может оставить смену статуса без события.

> **Уточнение 2026-10-13.** Ранее здесь было написано, что функция множество не
> проверяет, что противоречило следующему за абзацем пункту «Следствия»:
> множество обеспечивается кодом — единственным местом, пишущим `reopened`.
> Утверждение уточнено: **проверку выполняет функция**.

**Существующие ограничения это допускают.** Проверено по определениям
`CHECK`-ограничений в рабочей базе:

- `ck_document_verification_events_rejected_reason` обращается к `reason` **только**
  при `event_type = 'rejected'`, поэтому код в `reopened` он не затрагивает;
- ограничения вида `reason IS NULL` **не существует ни для одного** `event_type`;
- `ck_document_verification_events_reopened_origin` требует `from_status` из
  `{verified, rejected}`, `ck_document_verification_events_type_matches_target` —
  `to_status = 'pending'`: оба выполняются.

**Следствия:**

- **Новые колонки не требуются.**
- **Новые `CHECK`-ограничения в MVP не добавляются.** Множество значений
  обеспечивается кодом — единственным местом, пишущим `reopened`. Ограничение на
  уровне базы потребовало бы миграции и отдельного решения о том, что делать со
  строками, где `reason IS NULL`.
- **Существующие исторические записи не изменяются.** Заполнение `reason`
  относится только к новым событиям; обновление уже записанных строк
  запрещено.

### Транзакции и конкурентный доступ

1. **Один `commit` на операцию.** Изменение метаданных файла, изменение
   `verification_status` и вставка события истории фиксируются **одной**
   транзакцией. Промежуточных коммитов нет.
2. **Коммит принадлежит `FileService`.** Файловая операция — единственная,
   которая пишет в две таблицы, поэтому владение транзакцией переносится на неё.
   Внутренние шаги не коммитят; коммит делает только публичный метод.
3. **Блокировка документа.** Каждая мутирующая операция начинается с
   `SELECT ... FOR UPDATE` по строке `documents`. Блокировка удерживается до
   коммита или отката и сериализует все изменения одного документа; разные
   документы не блокируют друг друга.
4. **`populate_existing=True` обязателен.** Блокирующий `SELECT` возвращает
   экземпляр из identity map **с устаревшими атрибутами**, если объект уже
   загружен в сессии: без `populate_existing` второй транзакции не увидит
   изменение первой и запишет повторное событие `reopened`, нарушив правило 6.
   Применяется **до любых мутаций** соответствующего ORM-объекта.
5. **Та же стратегия в `DocumentService`** — в `update`, `verify` и `reject`.
   Без этого верификация обходила бы блокировку и правило 6 снова переставало бы
   действовать.
6. **Компенсация записи файла.** Файл пишется на диск **до** регистрации строки.
   Если транзакция не сошлась, выполняется `rollback()` и физическое удаление
   файла.
7. **Физическое удаление — только после коммита удаления метаданных.** Обратный
   порядок создал бы обратное и неприемлемое состояние: строка `files` уцелела
   бы, а файл был бы удалён — документ утверждал бы, что файл есть, а его нет.
8. **Ошибки до и после коммита различаются явно.** Ошибка **до** коммита
   откатывает транзакцию и проваливает запрос. Ошибка **после** коммита — уже не
   откатывает ничего: она логируется, а запрос завершается успехом, потому что
   логическая операция состоялась.

### Границы гарантий

**Атомарность PostgreSQL и файловой системы не обеспечивается и не
утверждается.** У них нет общей транзакции: `COMMIT` в PostgreSQL ничего не
знает о файловой системе, а удаление файла ничего не знает о PostgreSQL.

Заявляемая гарантия — **атомарность метаданных плюс компенсация побочных
эффектов**:

> Транзакция PostgreSQL охватывает строку `files`, изменение
> `verification_status` и событие истории: они либо сохраняются все, либо не
> сохраняется ни одно. Физический файл в транзакцию не входит — его появление
> или исчезновение компенсируется программно.

**Остаточный риск — аварийное завершение процесса.** Компенсация не выполняется,
если процесс убит между файловой операцией и коммитом: остаётся файл без строки
в базе. Это **потеря дискового места, а не потеря данных**, и она обнаружима
сверкой, но не предотвращается.

**Требуется будущая сверка.** Периодический обход `storage/` с поиском файлов,
для которых в `files` нет строки с таким `storage_key`. Схема для этого не
требуется: `storage_key` уже уникален, а имя индекса соответствует конвенции
проекта. Сверка — отдельное задание, не входящее в объём этого ADR.

## HTTP-контракт

Роутер: `APIRouter(prefix="", tags=["files"])` — путь целиком задаётся
вложенностью, как уже сделано в `variants`.

| Операция | Метод и URL | Успех |
| --- | --- | --- |
| Загрузка | `POST /documents/{document_id}/files` | **`201`**, заголовок `Location`, тело `FileOut` |
| Список | `GET /documents/{document_id}/files` | **`200`**, голый JSON-массив `FileOut[]` |
| Метаданные | `GET /documents/{document_id}/files/{file_id}` | **`200`**, `FileOut` |
| Скачивание | `GET /documents/{document_id}/files/{file_id}/content` | **`200`**, поток ответа |
| Удаление | `DELETE /documents/{document_id}/files/{file_id}` | **`204`**, без тела |

### Ошибки

| Код | Когда |
| --- | --- |
| `404` | документ отсутствует; файл отсутствует; строка принадлежит другому документу; **строка есть, а физического файла нет** |
| `413` | файл превышает `MAX_UPLOAD_SIZE_BYTES` |
| `422` | недопустимое имя (пустое, с NUL, длиннее 255); пустой файл; неподдерживаемый формат |

### Ответ

`FileOut` содержит `id`, `document_id`, `original_filename`, `mime_type`,
`size_bytes`, `sha256`, `uploaded_at`.

**`storage_key` в публичный ответ не выводится.** Это внутренний путь на диске;
его раскрытие не требуется клиенту и раскрывает структуру хранилища.

Коллекция возвращается голым JSON-массивом, как `DocumentListOut` и все
существующие коллекции проекта, — без `total`.

### Скачивание

- **`Content-Disposition` строится с экранированием.** Имя файла хранится дословно
  и может содержать CR, LF, кавычки и обратный слэш. Значение подставляется в
  ASCII-варианте с удалением управляющих символов и в варианте `filename*=UTF-8''`
  по RFC 5987 с процентным кодированием. Управляющие символы в заголовок не
  попадают ни в одной форме.
- **`Content-Length` из метаданных базы не подставляется.** Значение
  `size_bytes` записано при загрузке и может разойтись с фактическим содержимым.
  В MVP заголовок не проставляется; ответ уходит чанками. Если он появится в
  будущем, он обязан опираться на реальный поток, а не на строку в базе.
- **Отдельный `HEAD` в MVP не вводится.**
- **Физически отсутствующий файл при существующей строке базы — `404`** с
  обязательной диагностикой: состояние означает нарушение целостности хранилища
  и должно попасть в лог, а не остаться незамеченным.

## Миграции и конфигурация

### Требуется миграция

**Индекс `ix_files_document_id_id` на `(document_id, id)`.**

Обоснования:

- у всех трёх таблиц связей индексы на внешнем ключе уже есть
  (`ix_document_variants_variant_id`, `ix_document_products_product_id`,
  `ix_document_batches_batch_id`) — отсутствие такого индекса у `files` нарушает
  конвенцию проекта;
- `ON DELETE CASCADE` выполняет удаление по `document_id`, а PostgreSQL не
  индексирует внешние ключи на стороне ссылающейся таблицы автоматически;
- составной порядок `(document_id, id)` обслуживает и фильтр, и сортировку
  списка вложений по возрастанию `id`.

Имя соответствует конвенции `ix_<table>_<столбцы>`.

**Эта миграция не создаётся в рамках принятия решения** и выполняется отдельным
заданием. Правила настоящего ADR от неё не зависят.

### Обязательная зависимость

**`python-multipart`** должен быть добавлен в `requirements.txt`. Без него
определение маршрута с `UploadFile` завершается `RuntimeError` при импорте
модуля — приложение не запускается.

### Конфигурация

| Настройка | Использование |
| --- | --- |
| `STORAGE_ROOT` | корень `LocalStorageBackend`; сегодня объявлен, но не используется |
| `MAX_UPLOAD_SIZE_BYTES` | лимит загрузки; сегодня объявлен, но не используется, а значение продублировано в `app/config.py` и `app/services/file_service.py` |

Обе настройки перестают быть мёртвыми: их чтение переносится в
`app/dependencies.py`, который собирает `FileService` из `get_db` и `Settings`.

## Безопасность

| Мера | Решение |
| --- | --- |
| Определение формата | **по сигнатуре содержимого**, не по расширению и не по `Content-Type` от клиента |
| Физический путь | **UUID4** в имени файла и `document.id` в каталоге: имя, присланное клиентом, в путь **не попадает** |
| Защита от обхода путей | `LocalStorageBackend._resolve()` — относительность, запрет NUL, POSIX-разделители, запрет сегмента `..`, проверка результата `resolve()` на принадлежность корню |
| Имя в HTTP-заголовках | экранирование при формировании `Content-Disposition` |
| Передача | потоковая, без чтения тела в память |
| Целостность содержимого | SHA-256 **вычисляется и хранится**, но **не сверяется**. Проверка при чтении или в сверке — **будущее задание** |

### Граница безопасности

**Этот этап не вводит аутентификацию и авторизацию.** Все пять маршрутов
анонимны: любой, кто обращается к приложению, читает и удаляет любые вложения.

Это сознательная граница, а не упущение:

- скрытие `storage_key` защищает от утечки структуры хранилища, **но не от
  доступа**: `content` отдаёт байты по `file_id`, который последователен и
  предсказуем;
- модель `File` не содержит признака владельца, поэтому разделение документов по
  пользователям или организациям потребует новой колонки и новой миграции — это
  выходит за объём настоящего ADR.

**Запрет:** публичное развёртывание анонимного File API **запрещено** до
реализации аутентификации и авторизации. Вложения — персональные данные, и
маршруты `content` и `delete` не должны выставляться наружу. На этапе разработки
приложение доступно только локально.

## Последствия

**Положительные**

- Подтверждение документа становится достижимым для пользователя: появился путь,
  на котором `verify` получает требуемое вложение.
- Изменение состава вложений оставляет такой же проверяемый след, как изменение
  реквизитов: `reopened` с причиной `file_added` или `file_deleted`.
- Аудитор различает «правили номер документа» и «заменили скан» — без кода в
  `reason` оба случая выглядели одинаково, а удаление файла вообще не оставляло
  следов.
- Правила проверки и правила файлов живут в одном механизме, поэтому третий
  источник перехода не потребует второго места записи.
- Компоновка транзакции исключает состояние «файл записан, но метаданных нет»
  для всех штатных путей ошибок.

**Отрицательные**

- **Состав вложений нельзя править у подтверждённого документа без потери
  вердикта.** Даже замена одного скана из трёх возвращает документ в `pending` —
  это прямое следствие правила 4.
- Анонимный API — сознательный риск, сдерживаемый только запретом на публичное
  развёртывание.
- Загрузка занимает соединение с базой на всё время передачи тела: временного
  файла на диске сервер не создаёт, а это ограничение текущей архитектуры.
- В журнале истории появился машинный код на человеческом месте. Читать историю
  нужно с учётом того, что `reason` события `rejected` — текст, а `reason`
  события `reopened` — код.

## Ограничения

- Решение **не вводит** аутентификацию, авторизацию, квоты и ограничения по
  числу вложений.
- Решение **не вводит** диапазонные запросы (`Range`), ETag и `HEAD`: поток
  возвращается целиком.
- Решение **не утверждает** сверку SHA-256 при чтении: значение хранится, но
  сравнение — будущее задание.
- Решение **не утверждает** автоматическую сверку осиротевших файлов как
  обязательную; она названа необходимой, но выполняется отдельным заданием.
- Решение **не изменяет** `passive_deletes` на связи `File.document`:
  ORM-удаление документа с вложениями по-прежнему падает по `NOT NULL`, хотя в
  базе объявлен `ON DELETE CASCADE`. Это отдельный вопрос, впервые поднятый в
  ADR-008.
- Решение **не рассматривает** срок давности статуса: истечение `valid_to` не
  возвращает документ в `pending` автоматически.
- **Закрытое множество причин проверяется кодом, а не базой.** `CHECK` на
  `reason` для `reopened` не добавлен: он потребовал бы миграции и отдельного
  решения о строках, где `reason IS NULL`. Любая запись в обход `record_reopened`
  обходит эту проверку — ограничение держится на дисциплине вызывающего кода.
- Ссылка на этот ADR из кода **проставлена частично**: `app/services/document_service.py`
  вызывает `record_reopened` без текстовой ссылки на документ. Ссылки в коде
  появятся вместе с файловой частью решения, когда изменение кода будет
  разрешено.

## Нерешённые вопросы

1. **Сверка SHA-256** — при чтении, в сверке или не выполнять вовсе.
2. **Сверка осиротевших файлов** — расписание, способ запуска, форма отчётности.
3. **Ошибка компенсации.** Сегодня `_cleanup` глушит исключение
   (`except Exception: pass`), и неудачная очистка остаётся незамеченной.
   Введение журналирования — первое использование `logging` в проекте.
4. **Аварийное завершение между файловой операцией и коммитом** — ловить ли
   `BaseException` вместо `Exception`. Обсуждалось, не решено.
5. **Аутентификация и авторизация** — вне объёма; до их реализации анонимный
   File API не разворачивается публично.
6. **Заголовок `ETag` или `Last-Modified`** для маршрута скачивания.
7. **Прямая выдача URL вместо проксирования** через приложение — требует решения
   по правам доступа.
