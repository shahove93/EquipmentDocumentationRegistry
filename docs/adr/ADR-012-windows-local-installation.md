# ADR-012: Устанавливаемый локальный режим для Windows

- Статус: Предложено к реализации в первом этапе
- Дата: 2026-10-27
- Контекст: после завершения MVP + Batch продукт нужно устанавливать небольшим
  компаниям без ручной настройки среды разработки.

## Контекст и проблема

Текущий продукт запускается в WSL2 и требует отдельной установки Python,
PostgreSQL и Node.js. Такой путь подходит разработчику, но неудобен для пилота
у небольшой компании. Документы и вложения должны оставаться на компьютере
компании, а резервная копия должна сохранять связанность записей БД и файлов.

## Решение

Первой поставкой станет устанавливаемый локальный режим для одного Windows-
компьютера:

- установочный пакет ставит runtime приложения, production-сборку frontend и
  локальный PostgreSQL; пользователь не настраивает WSL, Python, PostgreSQL,
  Node.js или Docker вручную;
- если приложению нужен Microsoft Visual C++ x64 Runtime, а подходящий runtime
  отсутствует, установка показывает понятное сообщение и открывает официальную
  страницу загрузки Microsoft. EDR не включает и не распространяет CRT DLL или
  `vc_redist` пакет;
- приложение обслуживает интерфейс локально и открывает его в браузере;
- API слушает только loopback-интерфейс (`127.0.0.1`), сетевой доступ не
  включается;
- база PostgreSQL и вложения находятся в выделенных каталогах данных вне
  каталога установки, чтобы обновление приложения и его удаление не удаляли
  рабочие документы;
- предусмотрены операции запуска, остановки, обновления схемы, резервного
  копирования и восстановления согласованного набора «БД + вложения»;
- удаление приложения по умолчанию сохраняет каталог данных; удаление данных
  оформляется отдельным явным действием с предупреждением.

Существующие React/Vite, FastAPI и PostgreSQL сохраняются. Технологию упаковки
и Windows service wrapper следует выбрать в рамках TASK после проверки
совместимости с текущей конфигурацией и воспроизводимого smoke-пакета.

## Рассмотренные варианты

1. **Оставить инструкцию WSL2.** Не решает клиентскую установку.
2. **Требовать Docker Desktop.** Упрощает запуск контейнеров, но добавляет
   отдельную обязательную установку и администрирование Docker на ПК клиента.
3. **Локальный Windows-пакет с приложением и PostgreSQL.** Выбран: один
   понятный путь установки, локальное хранение и совместимость с текущей БД.
4. **Переписать UI как нативное desktop-приложение.** Отложено: браузерный UI
   уже работает через API, а отдельная оболочка не решает хранение, резервное
   копирование и сопровождение локальной БД.

## Последствия и границы

- Первый этап рассчитан на одного пользователя за одним Windows-компьютером.
- Несколько компьютеров и доступ по LAN/VPN не входят в этот этап: продукт пока
  не имеет аутентификации и авторизации.
- Публичное размещение и облачное хранение не входят в этот этап.
- Резервная копия должна включать БД и все blob-файлы; копирование только одной
  из частей не считается успешной резервной копией.
- В исключительном случае отсутствия VC++ runtime установке потребуется
  интернет для открытия страницы Microsoft и отдельное подтверждение установки
  runtime пользователем; пакет CRT в поставку EDR не входит.
- Обновление схемы должно завершаться до запуска новой версии и не должно
  удалять пользовательские данные при ошибке.
- Локальный WSL2 development workflow сохраняется.

## Проверяемые критерии

- Чистая Windows x64 установка не требует установленной среды разработки или
  Docker.
- После запуска пользователь может открыть интерфейс через ярлык; порт API
  доступен только с этого компьютера.
- Созданные записи и загруженные вложения сохраняются после перезапуска.
- Резервная копия и восстановление возвращают записи и соответствующие файлы.
- Обновление/удаление приложения сохраняет каталог данных по умолчанию.
- Документация явно объясняет расположение данных, резервную копию и ограничения
  локального режима.
