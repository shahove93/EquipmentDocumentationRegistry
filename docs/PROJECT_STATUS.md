## Технологический стек

| Слой | Технология | Версия |
| --- | --- | --- |
| Web | FastAPI | 0.142.2 |
| ASGI-сервер | uvicorn[standard] | 0.54.0 |
| ORM | SQLAlchemy 2.x (`DeclarativeBase`, `Mapped`/`mapped_column`) | 2.1.3 |
| Миграции | Alembic | 1.20.0 |
| Валидация | Pydantic v2 + pydantic-settings | 2.13.5 / 2.15.0 |
| БД | PostgreSQL (драйвер `psycopg` 3) | сервер 18.6 |
| Тесты | pytest + httpx + `fastapi.testclient` | pytest 9.1.1 |

Архитектурный стиль — **вертикальные срезы**: `модель → схема → сервис → роутер →
тесты`. Слои связаны напрямую, без репозиториев и абстракций unit of work.
Транзакционные границы: сервис коммитит сам, ровно один раз на операцию; методы
чтения не коммитят. Общий **механизм** владения транзакцией и блокировки строк —
`app/services/transaction.py`; им пользуются и `DocumentService`, и `FileService`,
хотя **политика** у них разная: `DocumentService` усыновляет открытую на входе
транзакцию, `FileService` от неё отказывается.

## Пока не реализовано

| Что | Комментарий |
| --- | --- |
| **Document API** | Ни одного маршрута для документов. Модель `Document`, Pydantic-схемы и `DocumentService` готовы и покрыты тестами; не подключены к приложению |
| **API загрузки и скачивания файлов** | `FileService` и `LocalStorageBackend` готовы, но не подключены к HTTP-слою. Из-за этого `verify` недостижим для пользователя. Контракт пяти маршрутов принят в [ADR-009](adr/ADR-009-document-attachments.md); **HTTP-реализации нет**, `python-multipart` не установлен |
| **BatchService и Batch API** | Модель `Batch` есть, сервиса и маршрутов нет |
| **HTTP-операции привязки документов** | Привязка документов к изделиям, вариантам и партиям на уровне API не реализована — см. [связь сертификатов с типоразмерами](adr/DOCUMENT-VARIANT-RELATIONSHIP.md) |

Итог: центральная сущность предметной области — **документ** — пока недоступна
через HTTP. На уровне модели, схем и сервисов она закрыта полностью, включая
жизненный цикл проверки и его историю.

## Реализовано и принято, но не выполнено

**Реализованные функции** (подтверждены кодом и тестами): `DocumentService` с
полным жизненным циклом верификации и атомарной историей; общий модуль
`app/services/transaction.py`; `FileService.attach()` / `detach()` / `upload()` /
`list_for_document()`; автоматический возврат в `pending` с событием `reopened`
(`file_added`, `file_deleted`); компенсация добавления; удаление файла только
после подтверждённого `commit`; журналирование через `logging`; доменные ошибки
`AttachmentNotFoundError`, `TransactionAlreadyOpenError`,
`PendingDocumentChangesError`.

**Решения приняты, но не выполнены** (обязательны к исполнению, доказательства в
коде отсутствуют): постоянное хранилище журнала; сверка осиротевших файлов;
сверка SHA-256; HTTP API документов и файлов; миграция `ix_files_document_id_id`;
аутентификация и авторизация. Построчный перечень — в разделах «Статус
реализации» [ADR-009](adr/ADR-009-document-attachments.md) и «Ограничения» ниже.

## Рекомендуемый следующий этап

**1. Финальная проверка и фиксация текущей реализации в Git.**

Девять файлов ждут фиксации: общий модуль `app/services/transaction.py`, перевод
на него `DocumentService`, реализация `FileService.attach()` / `detach()`,
`upload()` как обёртка, доменная ошибка `AttachmentNotFoundError` и три
тест-файла. Код достиг состояния, при котором его можно фиксировать: одна
транзакция на операцию, блокировки строк, освобождение на путях отказа и no-op,
автоматический возврат в `pending`, журналирование. Изменения кода больше не
требуются — нужен только commit/push.

**2. File HTTP API — следующая функциональная веха.**

Транзакционный контракт `attach` / `detach` **уже реализован**; осталась
транспортная оболочка. Порядок работ определяется тремя причинами:

- `DocumentService.verify` требует хотя бы одного прикреплённого файла, а
  загрузить файл через приложение сейчас нельзя: весь подтверждённый жизненный
  цикл программный. File API — то, что делает `verify` достижимым для
  пользователя;
- `python-multipart` **не установлен**. Пока его нет, определение маршрута с
  `UploadFile` обрывает импорт приложения, поэтому зависимость добавляется
  первой;
- `Settings.STORAGE_ROOT` и `Settings.MAX_UPLOAD_SIZE_BYTES` объявлены, но не
  используются production-кодом — их задействование естественно ложится на этот
  этап вместе с `app/dependencies.py` и `get_file_service`.

Состав работ:

1. **Обязательная зависимость.** Добавить `python-multipart` в
   `requirements.txt` и установить его.
2. **Контракт маршрутов.** Форма соответствует уже принятому образцу: `POST` с
   телом файла + `Location`, `GET` списка вложений документа, скачивание по
   `storage_key`; 404 для неизвестного документа или файла, 422 — валидация типа
   и размера, 409 — открытая на входе транзакция.
3. **DI.** `app/dependencies.py` с `get_file_service`; `FileService` сейчас
   создаётся вручную и нигде не инстанцируется приложением.
4. **Отложенная миграция.** Индекс `ix_files_document_id_id`, см. ограничение 16.
5. **Постоянное хранилище журнала.** Настроить обработчики `logging`, чтобы
   записи компенсации переживали перезапуск процесса.

**Остаётся вне этого этапа:** сверка осиротевших файлов, сверка SHA-256,
аутентификация и авторизация (до неё публичное развёртывание File API запрещено),
Document API и операции привязки документов.

**Затем — Document API.** Проектирование его контракта уже частично выполнено:
модель `Document`, схемы `DocumentCreate` / `DocumentUpdate` / `DocumentOut` и
`DocumentService` существуют, а правила верификации зафиксированы в
[ADR-008](adr/ADR-008-document-verification-lifecycle.md). Открытыми остаются:

1. **Отображение доменных ошибок на коды ответа.** `DocumentTypeNotFoundError`
   и `IssuerNotFoundError` — 404 либо 422, `InvalidValidityPeriodError` — 422,
   `DocumentHasNoFilesError` и `RejectionReasonRequiredError` — решение
   требуется. Они возникают при `PATCH` и при подтверждении, то есть в маршрутах,
   которых ещё нет.
2. **`PATCH /documents/{id}` не принимает `verification_status`** — это
   зафиксированное решение, а не пробел. Подтверждение и отклонение получают
   отдельные маршруты; их форма ещё не выбрана.
3. **`document_type_id` обязателен** (`NOT NULL`), и справочник по умолчанию
   пуст — нужно решить, чем отвечать на попытку создать документ в пустом
   справочнике.
4. **Затем — операции привязки** документов к изделиям, типоразмерам и партиям,
   см. [связь сертификатов с типоразмерами](adr/DOCUMENT-VARIANT-RELATIONSHIP.md).

Готовый образец для копирования структуры: `app/api/issuers/` +
`app/services/issuer_service.py` и соответствующие четыре тест-файла
(`test_issuer.py`, `test_issuer_schemas.py`, `test_issuer_service.py`,
`test_issuers_api.py`). Для `documents/` образец уже наполовину собран:
`app/api/documents/` содержит схемы без роутера.

## Карта проекта

```
app/
├── main.py                 точка входа, подключение роутеров
├── config.py               Settings; маскирование DATABASE_URL в repr/выводе
├── api/
│   ├── router.py           /health + подключение пяти роутеров
│   ├── manufacturers/      router.py + schemas.py
│   ├── products/           router.py + schemas.py
│   ├── variants/           router.py + schemas.py (без prefix)
│   ├── document_types/     router.py + schemas.py
│   ├── issuers/            router.py + schemas.py
│   └── documents/          schemas.py (роутера нет)
├── database/connection.py  engine, SessionLocal, get_db
├── models/                 11 модулей + __init__.py с реэкспортом
└── services/               6 сервисов сущностей
                            + transaction.py  общий механизм блокировки и транзакции
                            + verification_history.py  общий механизм reopened
                            + file_service.py
                            + storage.py (ABC) + local_storage.py
alembic/versions/           12 ревизий
tests/                      37 файлов тестов + conftest.py
docs/                       эта документация
```

Тесты покрывают каждый слой отдельно: модель, схемы, сервис, HTTP. Общая
фикстура `engine` создаёт временную схему `test_file_service`, поднимает в ней
таблицы через `Base.metadata.create_all` и удаляет схему после теста — поэтому
тесты **изолированы от схемы `public`** рабочей базы.
