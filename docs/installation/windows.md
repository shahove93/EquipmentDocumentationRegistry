# EDR: локальная установка Windows x64

Предназначено для одного пользователя одного компьютера Windows 10/11 x64.
Приложение открывается в обычном браузере. Доступ с других компьютеров, LAN/VPN,
роли и облачное хранение не предусмотрены. WSL, Docker, Python, Node.js и
PostgreSQL пользователю устанавливать не нужно.
Microsoft Visual C++ v14 Runtime x64 (минимум 14.44) включён в EXE EDR.
Подходящая или более новая установленная версия пропускается; отсутствующая
устанавливается тихо под тем же повышением прав до подготовки ProgramData.
Интернет и отдельное скачивание пользователем не нужны. Ошибка prerequisite
останавливает установку EDR. При запросе перезагрузки перезагрузите Windows
и повторно запустите setup. Журнал `EDR-vcredist.log` находится во временном
каталоге setup.

## Установка и работа

1. Запустите `EDR-0.2.0-windows-x64.exe` под своей обычной учётной записью.
   Установщик запрашивает права администратора для защищённого ProgramData.
   Можно выбрать каталог программы с кириллицей, Unicode и пробелами.
   Пользователем EDR остаётся владелец интерактивной оболочки рабочего стола,
   даже если в UAC введены данные другой административной учётной записи.
   При недоступной или другой интерактивной оболочке установка отменяется.
   Не запускайте приложение от администратора: PostgreSQL этого не допускает.
2. Откройте ярлык **EDR** на рабочем столе или в меню «Пуск». При первом запуске
   создаются отдельная база и схема. Дождитесь открытия браузера.
3. Интерфейс: `http://127.0.0.1:18765/`. API и UI работают на одном адресе,
   PostgreSQL — только на `127.0.0.1:55432`. Порты фиксированы; конфликт порта
   останавливает запуск, а не переключает приложение на сетевой интерфейс.
4. Закрытие вкладки браузера не останавливает EDR. Для остановки используйте
   **Stop EDR** в меню «Пуск». Повторный запуск ярлыка открывает имеющийся процесс.

Программа по умолчанию: `%ProgramFiles%\EDR`; можно выбрать другой каталог.
PostgreSQL отдельно: `%ProgramData%\EDR\runtime\postgresql`.
Данные: `%ProgramData%\EDR\state\data`. Внутри находятся `postgres` (кластер БД), `attachments`
(вложения), `logs` (журналы), `runtime.json` (настройки и локальный пароль БД).
Локальные резервные копии можно хранить в `%ProgramData%\EDR\state\backups`.
ACL данных разрешает доступ только предназначенной учётной записи и SYSTEM.
Administrators, Users и Everyone не получают ACE на данные и backups.
Отдельный `control/gate` содержит только пустой файл блокировки: SYSTEM и
Administrators имеют FullControl, intended SID — ReadAndExecute; наследование
отключено. Корень и runtime имеют такие же установочные ACL. Секреты и
пользовательское содержимое в control не хранятся.
Владельцем `state` и защищаемых дочерних объектов может быть
`BUILTIN\Administrators` (явный waiver 2026-11-03). Владение не добавляет ACE на
данные: Administrators не получает прямого чтения/записи. Локальный
администратор может изменить DACL как owner; дополнительная защита данных от
локальных администраторов Windows не требуется. Обычные пользователи,
Administrators и Everyone по-прежнему не имеют ACE на данные и backups.
`owner.json` в защищённом корне хранит SID пользователя и
исходный путь старых данных; другая Windows-учётная запись не запускает EDR.
Не меняйте `owner.json`, `runtime.json`
и не переносите отдельно одну из частей данных. Это локальный режим без
пользовательской авторизации; доступ к Windows-профилю даёт доступ к документам.

Путь ProgramData должен быть ASCII (обычно `C:\ProgramData`). Установщик
отклоняет Unicode ProgramData и reparse points. Временные диски, псевдонимы и
короткие имена 8.3 не используются. Каталог самой программы может быть Unicode.
Нестандартный `--data-dir` допускается только внутри защищённого
`%ProgramData%\EDR\state` и должен иметь ASCII-путь. Системную кодировку менять
не требуется. Ярлыки устанавливаются в общее меню «Пуск» и, по выбору, на общий
рабочий стол; пользоваться данными может назначенная учётная запись.

Перед первым обновлением старой per-user поставки остановите её через старый
**Stop EDR**. При первом запуске новая версия копирует
`%LOCALAPPDATA%\EDR\data` исходного пользователя в закрытый staging внутри
ProgramData, проверяет размеры/SHA-256, запускает копию кластера и проверяет
соответствие записей вложениям. Только после успешной остановки проверенной
копии каталог атомарно переименовывается в `state\data`. Исходник сохраняется
и после успеха. При ошибке приложение не переключается на staging; исходник
и неудачный staging остаются для диагностики. Не запускайте старую версию
после перехода: она использует сохранённую старую копию, а не новые данные.

При ошибке приложение показывает сообщение и сохраняет исходные данные.
Проверьте свободное место, занятые порты и журналы. Не удаляйте каталог данных
ради повторного запуска. После сбоя питания следующий запуск останавливает
оставшийся локальный PostgreSQL и выполняет обычное восстановление кластера.

## Резервная копия

Сначала остановите EDR. Откройте **Командную строку** и выполните:

```bat
"C:\Мои программы\EDR\EDR.cmd" stop
"C:\Мои программы\EDR\EDR.cmd" backup "%ProgramData%\EDR\state\backups\2026-10-28.zip"
```

Замените `C:\Мои программы\EDR` выбранным каталогом программы.
Родительский каталог копии должен существовать. Имя ZIP должно быть новым;
существующая копия не перезаписывается. Windows принимает только файлы прямо
в `%ProgramData%\EDR\state\backups`; другие назначения отклоняются до записи.
Частичный файл и готовый ZIP наследуют ACL intended SID и SYSTEM.
Во время операции запуск интерфейса
заблокирован. Архив содержит PostgreSQL custom dump, все вложения и manifest
с размерами и SHA-256. Временный архив публикуется только после успешной записи.
Копия не зашифрована: храните её с соответствующим доступом.

После успешного завершения (код 0) снова откройте EDR. Ошибка (код 1) означает,
что новую копию нельзя считать готовой. Обычное копирование работающего каталога
`postgres` или только `attachments` не заменяет резервную копию.

## Восстановление

Остановите EDR. Восстанавливать можно **только в пустой или новый каталог**;
существующая база и файлы никогда не заменяются командой restore.

```bat
"C:\Мои программы\EDR\EDR.cmd" restore "%ProgramData%\EDR\state\backups\2026-10-28.zip" --data-dir "%ProgramData%\EDR\state\recovered"
"C:\Мои программы\EDR\EDR.cmd" start --data-dir "%ProgramData%\EDR\state\recovered"
```

Проверяются состав, пути, размеры и SHA-256 архива. База и файлы разворачиваются
в отдельный закрытый staging-каталог; только после успешного восстановления и
остановки PostgreSQL он становится целевым каталогом. При ошибке исходные
данные остаются на месте, staging сохраняется для диагностики.

Для возврата на стандартный путь переименуйте прежний `data`, сохранив его как
страховочную копию, и восстановите архив без `--data-dir`. Не удаляйте прежние
данные до проверки записей и скачивания вложений. Нестандартный `--data-dir`
нужно передавать во всех командах; стандартные ярлыки используют стандартный путь.
Перед обновлением или удалением остановите также такие нестандартные экземпляры.

## Обновление и удаление

Перед обновлением сделайте резервную копию. Запустите новый установщик под той
же Windows-учётной записью в тот же каталог программы. Установщик сначала
проверяет общий шлюз всех runtime roots, включая `state/recovered`. При активном
start, stop, backup или restore операция сразу отменяется: остановите каждый
экземпляр с его `--data-dir`, дождитесь завершения операций и повторите.
Maintenance marker исключает запуск во время замены файлов. Экспериментальные
установки без `control/gate` отклоняются без изменения данных и требуют отдельно
согласованного контролируемого переноса. Данные находятся
вне каталога программы и при замене файлов не затрагиваются.

При изменении Alembic head приложение копирует активную БД в новую БД того же
кластера, применяет миграции к копии и атомарно переключает `runtime.json`
только после успеха. При ошибке исходная БД и вложения остаются прежними;
интерфейс новой версии не запускается. Старые БД автоматически не удаляются;
поэтому для обновления требуется место под дополнительную копию базы.
PostgreSQL major upgrade не выполняется автоматически: несовместимый кластер
сохраняется и запуск прекращается. Для этой поставки используется major 18.

Обновление и удаление также запрашивают права администратора. Для них нужно
работать на рабочем столе исходного пользователя. Установщик проверяет сохранённый
SID и отказывает при занятом общем шлюзе; установленный Python не
запускается от имени администратора. Если нельзя подтвердить пользователя или
остановить maintenance, операция отменяется. Чужую учётную запись UAC не
назначают владельцем существующих данных.

Стандартное удаление через Windows «Установленные приложения» удаляет программу,
PostgreSQL executables и ярлыки, сохраняя `%ProgramData%\EDR\state`, `owner.json`,
старый `%LOCALAPPDATA%\EDR\data` и резервные копии. Повторная установка
использует сохранённые данные. Отдельной команды автоматического удаления
пользовательских данных нет. Для окончательного удаления оператор отдельно
удаляет явно выбранный каталог средствами Windows после проверки копии.

## Сборка и выбранные компоненты

Выбраны Inno Setup **6.7.3**, CPython embedded **3.12.10 x64** и PostgreSQL
**18.6-5 x64** (архив EDB). React production build обслуживается FastAPI/ASGI
процессом. Вместо службы Windows используется per-user supervisor на Python:
он владеет lock каталога, запускает БД, выполняет миграции и держит API до
команды остановки. SCM/service wrapper не требуется; права администратора нужны
для установки/удаления, само приложение запускается обычным пользователем.

Альтернативы: PyInstaller требует проверки hooks для Alembic/psycopg и всё равно
не упаковывает жизненный цикл PostgreSQL; полноценная Windows-служба добавляет
права и управление сервисной учётной записью. Встроенный CPython позволяет
проверять именно поставляемый интерпретатор и wheel-зависимости без системного PATH.

Сборщик: Windows x64, Python 3.12 с pip, Inno Setup 6.7.3; frontend заранее
собирается Node.js 24.22.0 командами `npm ci`, `npm run typecheck`, `npm run build`.
Архивы Python и PostgreSQL передаются явно; Visual C++ скачивается при сборке.
На сборщике также должен быть установлен Microsoft CRT x64 >=14.44. Проверка
prerequisite встроена и в установщик, и в PowerShell launcher перед загрузкой
Python. Microsoft DLL не включаются в payload, в том числе удаляются две DLL
CRT из исходного Python embedded ZIP. Windows PowerShell 5.1 входит в Windows.

```powershell
./packaging/windows/build.ps1 -PythonArchive C:/build-inputs/python-3.12.10-embed-amd64.zip `
  -PostgresArchive C:/build-inputs/postgresql-18.6-5-windows-x64-binaries.zip `
  -UiDirectory C:/build-inputs/ui -WorkDirectory C:/edr-build-unique `
  -Iscc 'C:/Program Files (x86)/Inno Setup 6/ISCC.exe'
```

Сборка требует нового WorkDirectory и сохраняет версии wheel-пакетов и SHA-256
входных архивов в `build-manifest.json`. Лицензии Python, PostgreSQL/библиотек
и wheel dist-info включаются в payload; их нельзя удалять при распространении.
Для выпуска используйте проверенные источники и сверяйте происхождение архивов,
проверяйте подпись установщика и выполняйте smoke-проверку в чистой Windows VM.
Сам установщик EDR в этой реализации не подписывается автоматически.
Manifest содержит `selfContained=true` и объект `prerequisite` с точными version,
SHA-256, architecture, minimumVersion и данными подписи. Каждая сборка получает
пакет из `https://aka.ms/vc14/vc_redist.x64.exe` и проверяет действительную
Authenticode подпись Microsoft Corporation, подписанные метаданные x64 и версию
>=14.44.0.0. Сам PE bootstrapper может быть x86; проверяется архитектура runtime.
Новый EXE может приносить более новый поддерживаемый runtime. Microsoft binary
хранится только в WorkDirectory вне Git.
Ключ `-SmokeBuild` назначает отдельный AppId и корень `%ProgramData%\EDR-Smoke`,
чтобы тест не затрагивал регистрацию/данные штатной установки.
Прежний ключ `/EDRTestMissingCRT` больше не используется.

## Проверка поставки

`packaging/windows/smoke.ps1` допускает запуск только под WDAGUtilityAccount
в свежей Windows Sandbox и проверяет отдельную тестовую установку и синтетические
документы: запуск, запись/вложение, перезапуск, backup/restore, отказ от замены
существующих данных, копирование legacy с сохранением исходника, сохранность
при обновлении, удалении и переустановке. Параметр `-InstallDirectoryName`
позволяет проверить Unicode-путь. Настоящие UAC consent/credential prompts
требуют отдельного интерактивного подтверждения: Sandbox с `EnableLUA=0`
не доказывает эти сценарии. Проверка на рабочей
Windows с установленными инструментами **не равна чистой Windows VM**. Фактические
результаты и NOT_RUN перечисляются в отчёте исполнителя, принятие выполняется
отдельным ревьюером. Не используйте клиентские документы в smoke-проверках.

## Проверка установщика в GitHub Actions (Windows CI)

Отдельный job `.github/workflows/windows-installer.yml`
(`windows-installer`, `runs-on: windows-latest`) запускается **только вручную**
через `workflow_dispatch`; push/pull_request его не запускают. Права job —
`permissions: contents: read`, checkout с `persist-credentials: false`, задана
собственная группа `concurrency`. Существующий Ubuntu `ci.yml` не изменяется.

Job в одной эфемерной VM выполняет следующую цепочку:

1. `actions/setup-python@v7` ставит builder **CPython 3.12.10**,
   `actions/setup-node@v7` — **Node.js 24.22.0**; во `frontend` выполняются
   `npm ci` и `npm run build`.
2. Скачиваются официальные входы сборки и проверяются их закреплённые SHA-256
   (`Get-FileHash -Algorithm SHA256`, при несовпадении job падает):
   - CPython embedded `3.12.10` amd64,
     `https://www.python.org/ftp/python/3.12.10/python-3.12.10-embed-amd64.zip`,
     SHA-256 `4ACBED6DD1C744B0376E3B1CF57CE906F9DC9E95E68824584C8099A63025A3C3`;
   - EDB PostgreSQL `18.6-5` Windows x64 binaries,
     `https://get.enterprisedb.com/postgresql/postgresql-18.6-5-windows-x64-binaries.zip`,
     SHA-256 `E2246BA91D22345BC3D017586C09EDE52D9DF180B1EEB480F050445F1CAD84E2`.
   Эти значения взяты из существующего build contract
   (`TASK-WINDOWS-CRT-OFFLINE-01/manifest.json`,
   `TASK-WINDOWS-PROGRAMDATA-01-A1-C1-prerequisites/build-manifest.json`).
3. Ставится Inno Setup **6.7.3** с официального URL; job проверяет
   `FileVersion` установленного `ISCC.exe` и падает, если это не `6.7.3`.
   Версия подтверждается по `FileVersion`, а не по байтам: закреплённый SHA-256
   установщика Inno Setup не записан, поэтому байтовая воспроизводимость не
   гарантируется.
4. `packaging/windows/build.ps1` собирает установщик в новом `-WorkDirectory`
   с загруженными архивами, `frontend/dist`, найденным `ISCC.exe` и
   `-BuilderPython` из `setup-python`. Путь, размер и SHA-256 собранного EXE
   записываются в work-каталог.
5. `packaging/windows/ci-installer.ps1` сначала выполняет fail-closed guard:
   требует `GITHUB_ACTIONS=true`, `CI=true`, `RUNNER_OS=Windows`,
   `RUNNER_ENVIRONMENT=github-hosted`, отвергает узлы `EDR-Win11-Test` и
   `WDAG*`, а также существующие work/install каталоги и
   `%ProgramData%\EDR`. Только после этого он делает silent install
   (`/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /DIR=... /LOG=...`), проверяет
   наличие `python\python.exe`, `launcher.ps1`, `alembic.ini`, `ui\index.html`
   и `%ProgramData%\EDR\runtime\postgresql\bin\postgres.exe`.
6. `packaging/windows/ci-installer.py` запускается **установленным** bundled
   интерпретатором, стартует приложение как `app.windows_local start
   --no-browser`, ждёт `GET /health` = `{"status":"ok"}`, проверяет `GET /`
   (наличие `<div id="root">`), создаёт синтетические document type, документ и
   PDF-вложение, скачивает вложение и сверяет SHA-256; затем останавливает
   приложение, запускает снова, проверяет сохранность документа и неизменность
   SHA-256 вложения и останавливает снова.

Артефакты (`if: always()`, retention 14 дней) включают: work-каталог CI
(`install.log`, `results.json`, app/PostgreSQL logs, supervisor logs), собранный
EXE, `installer-exe.json`, `installer-exe.sha256`, `build-manifest.json` и
`build.log`.

### Что этот CI **не** проверяет

- Настоящий интерактивный UAC consent/credential prompt: runner — администратор,
  поэтому этот сценарий остаётся ручной проверкой.
- Установку на чистую пользовательскую Windows без предустановленных
  инструментов/зависимостей.
- Полный жизненный цикл (backup/restore, update/uninstall/reinstall, ACL/
  migration matrix) — это отдельный lifecycle TASK.
- Статус реального облачного запуска: **NOT_RUN** до фактического успешного
  запуска job в GitHub Actions; локальная статическая проверка не является
  подтверждением работоспособности установленного приложения.
